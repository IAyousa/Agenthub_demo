### 1.3 消息数据流（完整时序，含会话模式路由）

以下为一次用户与 Agent 对话的完整数据流转路径，支持单 Agent（direct）和多 Agent 群聊（group）两种模式：

```
步骤 1 ── 用户发送消息
   用户 ──► Vue Frontend (5173)

步骤 2 ── 前端通过 STOMP WebSocket 发送给 Java 后端
   Vue Frontend ──STOMP──► Spring Boot /ws-chat
   WebSocketController.handleUserMessage()

步骤 3 ── 持久化用户消息
   Spring Boot ──JPA save()──► H2
   写入 messages 表 (sender_type = "user")

步骤 4 ── 会话模式路由决策 + 上下文简化
   Spring Boot 查询 Agent 类型 → 解析 agentType/systemPrompt/workspace
   仅传当前消息文本（不再拼接历史 — CLI 通过 --continue 自行管理）

步骤 5 ── 转发给 Agent 服务
   Spring Boot (AgentGatewayService) ──HTTP POST──► FastAPI (8000)
   请求体: context=当前消息（纯文本）、agentType、systemPrompt、workingDirectory、conversationId

步骤 6 ── Agent 服务路由 + 会话状态判定
   messages.py: _session_tracker 判断 is_first_message
      True  → 注入 system_prompt + claude -p（创建新会话）
      False → claude --continue -p（恢复已有会话上下文）
   agentType 空 → Orchestrator 调度 ✓

步骤 7 ── Agent 流式响应返回
   CLI stdout / SSE stream ──► FastAPI
   SSE 事件流支持：agent_switch / chunk / finish

步骤 8 ── Agent 服务转发流式结果
   FastAPI ──SSE stream──► Spring Boot (WebClient SSE parser)

步骤 9 ── 逐块通过 STOMP 推送给前端
   Spring Boot (SimpMessagingTemplate) ──STOMP──► Vue Frontend
   如有产物生成写入 ./artifacts/ 并返回 preview_card
```

```mermaid

  U[👤 用户]
  FE[Vue 3 前端]
  BE[Spring Boot]
  DB[(H2 Database)]
  AG[FastAPI Agent 无状态网关]
```

### 1.3.1 WebSocketController 实现蓝图（已实施，步骤3已简化）

`WebSocketController.handleUserMessage()` 已实现。以下为当前实际逻辑（步骤3已从"构建结构化上下文"简化为"仅传当前消息"，由 CLI `--continue` 管理会话记忆）：

```java
@MessageMapping("/chat.send")
public void handleUserMessage(@Payload SendMessageRequest request) {
    // 步骤 1：保存用户消息（MessageService 已就绪）
    messageService.sendMessage(
        "system",                       // senderId（MVP 无用户系统）
        request.getConversationId(),
        request.getContent(),
        "text"
    );

    // 步骤 2：会话模式路由决策
    Conversation conv = conversationService.getConversationById(
        request.getConversationId()
    );
    String agentType = resolveAgentType(request, conv);

    // 步骤 3：只传当前消息 — CLI 通过 --continue 自行管理会话上下文
    String context = request.getContent().trim();

    // 步骤 4：转发给 Python Agent 服务
    agentGatewayService.sendToAgent(
        context,            // 仅当前消息文本
        agentType,
        systemPrompt,
        workspacePath,
        conversationId,
        token -> { /* SSE 流式推送 */ }
    );
}
```

> 依赖的 3 个 Service（ConversationService、MessageService、AgentGatewayService）均已完整实现，仅需在 Controller 中串联。

### 1.4 各层数据职责分工（关键设计原则）

```
┌─────────────────────────────────────────────────────────────────┐
│                        数据归属                                   │
│                                                                 │
│  Java 端 (Spring Boot)        │  Python 端 (FastAPI)            │
│  ┌───────────────────────┐    │  ┌───────────────────────────┐  │
│  │ 唯一的数据持久化层      │    │  │ 纯无状态协议转换网关      │  │
│  │ • 用户、会话、消息 CRUD │    │  │ • 零数据库访问           │  │
│  │ • 制品文件存储 ./artifacts│  │  │ • 不存储任何业务数据      │  │
│  │ • MVP: H2 文件模式持久化 │    │  │ • 职责: 接收结构化上下文  │  │
│  │ • P1: PostgreSQL 持久化  │    │  │   → 调用 CLI/HTTP Agent  │  │
│  └───────────────────────┘    │  │   → 流式转发 SSE 结果     │  │
│                                 │  └───────────────────────────┘  │
│                                                                 │
│  前端 (Vue 3)                                                   │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ 纯展示层                                                    │  │
│  │ • 通过 STOMP WebSocket 实时收发消息                          │  │
│  │ • 通过 REST API 获取历史数据                                 │  │
│  │ • 不直连数据库，不直连 Python Agent 服务                      │  │
│  │ • Vue Router 4 History 模式驱动 URL 单一真相来源             │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

&gt; **关键设计原则强调**：Java 后端是**唯一的数据权威**（Single Source of Truth）。Python Agent 服务是**零数据库访问的纯无状态网关**，只在请求生命周期内存在。这种架构完全避免了 Python 和 Java 之间的数据库耦合，两侧可以独立开发测试部署。

### 1.5 前端路由数据流（Vue Router v4）

C9 任务完成后，前端从"状态驱动"改造为"路由驱动"，URL 成为单一真相来源。以下为路由规范：

**当前路由表（router/index.ts）实际状态**：

| Path | Name | 组件 | 说明 |
|------|------|------|------|
| `/` | - | Redirect | 永久重定向 → `/chat/conv_frontend_001` |
| `/chat/:conversationId` | `chat` | `views/ChatView.vue` | 单聊视图（聊天气泡布局），动态路由参数为会话 ID |
| `/office` | `office` | `views/OfficeView.vue` | 办公室视图（SVG 场景），懒加载按需加载 |

**路由分发规则（待完善）**：点击会话时根据 `Conversation.type` 自动分发：
- `type === 'direct'` → 路由 `/chat/:conversationId` → ChatView
- `type === 'group'` → 路由 `/office/:conversationId`（P2 预留）→ OfficeView

**路由驱动数据流完整链路**：

```mermaid
flowchart TB
  U[用户点击会话]
  CL[ChatList.vue]
  R[Vue Router]
  CV[ChatView.vue watch route.params immediate]
  S[Pinia chatStore selectConversation]
  CW[ChatWindow.vue 渲染消息]

  U -- handleSelect --&gt; CL
  CL -- router.push('/chat/:id') --&gt; R
  R -- URL 变化 匹配路由 --&gt; CV
  CV -- watch 参数变化 --&gt; S
  S -- currentConversationId 变更 --&gt; CW
```

**关键特性说明**：
1. **`{ immediate: true }`**：ChatView 中的 watch 首次挂载时立即执行，直接访问 URL 不白屏
2. **History 模式**：干净 URL，无 `#`，生产环境 nginx 需配置 fallback 到 `index.html`
3. **命名路由判断激活态**：SideBar 用 `route.name === 'chat'` 而非 path.startsWith，与路径格式解耦
4. **OfficeView 懒加载**：`() =&gt; import()` 拆分 chunk，首屏不加载 SVG/GSAP 动画代码

## 3. Agent Service 分层架构说明

### 3.1 当前分层设计

Agent Service 采用简约分层架构，各层职责清晰解耦：

| 层级 | 说明 | 与外部依赖耦合度 |
|------|------|-------------|
| API 端点层 | FastAPI 路由处理器，参数校验 + 响应序列化 | 零耦合 |
| Pydantic 模型层 | AgentChatRequest/Response 数据定义 | 零耦合 |
| 适配器工厂层 | 根据 `agentType` 路由到对应适配器实例 | 零耦合 |
| 适配器实现层 | CLI 适配器（asyncio.subprocess）+ HTTP 适配器（httpx P1） | 与本地 CLI 工具或外部 HTTP 服务耦合 |

### 3.2 单 Agent 与多 Agent（Orchestrator）路由模式

```
POST /api/agent/chat
  → 检查 request.agentType
     ├── 有具体值 ("claude_code"/"codex"/"custom") → 单 Agent 模式
     │       直接调用对应适配器
     │       SSE 流不推送 agent_switch
     │       每个 chunk 携带统一的 agentId/agentName
     │
     └── 为空 (None / "orchestrator") → 多 Agent 群聊模式
             启动 Orchestrator
             LLM 动态生成任务执行计划
             推送 agent_switch 事件切换发言人
             每个 chunk 携带当前 Agent 的 agentId/agentName
```

- **单 Agent 模式**：用户手动选择 Agent 或会话默认关联单个 Agent，直接调用，流程简单
- **多 Agent 模式**：群聊场景，Orchestrator 调度器动态拆解任务、自动选择 Agent、串行/并行执行，支持 agent_switch 动态切换发言人
