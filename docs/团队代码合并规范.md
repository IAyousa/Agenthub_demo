## 一、分支命名与管理规范

### 1.1 分支类型

| 分支类型 | 命名格式 | 示例 | 说明 |
|---------|---------|------|------|
| 主干分支 | `dev` | `dev` | 日常开发集成分支，所有 feature/fix 分支合并目标 |
| 功能分支 | `feat-{简短描述}` | `feat-agent-gateway` | 新功能开发 |
| 修复分支 | `fix-{简短描述}` | `fix-a1a2a3` | Bug 修复或代码改进 |
| 发布分支 | `release-{版本号}` | `release-v1.0.0` | 发布前稳定与测试 |

### 1.2 分支生命周期

```
feat-xxx 分支创建 → 本地开发 → 推送前自检 → 创建 PR → Code Review → 合并到 dev → 删除 feat-xxx
```

> **规则**: 功能分支合并到 `dev` 后，**必须立即删除远程功能分支**，避免分支堆积。

### 1.3 分支同步策略

| 场景 | 操作 | 命令 |
|------|------|------|
| 开始新功能前 | 拉取最新 dev | `git checkout dev && git pull origin dev` |
| 开发过程中 | 定期 rebase dev | `git fetch origin dev && git rebase origin/dev` |
| 合并前 | 确保分支已同步 dev 最新代码 | `git merge origin/dev`（解决冲突后） |

## 二、Commit Message 编写规范

### 2.1 格式标准（Conventional Commits）

```
<type>(<scope>): <简短描述>

<详细说明（可选）>

<关联 Issue（可选）>
```

### 2.2 Type 类型定义

| Type | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(backend): 新增对话与消息服务层` |
| `fix` | Bug 修复 | `fix(frontend): 修复消息列表滚动定位异常` |
| `refactor` | 代码重构（不改变功能） | `refactor(agent): 提取 LLM 适配器为策略模式` |
| `docs` | 文档更新 | `docs: 新增 API 契约定义文档` |
| `style` | 代码格式调整（空格、缩进等） | `style(frontend): 统一缩进为 2 空格` |
| `test` | 测试代码 | `test(service): 补充 AgentGatewayService 单元测试` |
| `chore` | 构建/工具链/依赖变更 | `chore: 升级 Spring Boot 至 3.2.5` |
| `perf` | 性能优化 | `perf(backend): 优化消息查询分页索引` |

### 2.3 Scope 范围定义

| Scope | 对应模块 |
|-------|---------|
| `frontend` | Vue 3 前端 |
| `backend` | Spring Boot 主服务 |
| `agent` | Python FastAPI Agent 服务 |
| `docs` | 项目文档 |
| `infra` | 基础设施（Docker、CI/CD） |

### 2.4 编写范例

**好的 Commit Message**:

```
feat(backend): 新增对话与消息服务层，实现 Agent Gateway NDJSON 流式通信

- 新增 ConversationService：对话 CRUD、归档、Agent 关联
- 新增 MessageService：消息持久化、分页查询、上下文构建
- 升级 AgentGatewayService：从占位实现改为完整 NDJSON 流式解析
- 新增 MessageRepository 分页查询方法
- .gitignore 新增 backend-java/src/test/ 排除规则
```

**不好的 Commit Message**:

```
fix bug
update code
改了一些东西
```

> **Squash 合并时**，将多个零散 commit 压缩为一个语义化 commit，遵循上述格式编写完整的变更说明。

## 三、推送远程仓库前检查清单

> ⚠️ **这是最重要的环节。推送操作不可逆，请逐项确认。**

### 3.1 推送前必须确认的事项

| # | 检查项 | 验证方法 | 不通过的后果 |
|---|--------|---------|------------|
| 1 | **确认当前分支** | `git branch` 或 `git status` | 推错分支，污染远程仓库 |
| 2 | **确认目标远程仓库** | `git remote -v` | 推到错误的仓库 |
| 3 | **确认推送目标** | 明确 `git push origin <分支名>` | 默认推送可能覆盖不期望的分支 |
| 4 | **本地代码已编译通过** | `mvn compile -q` 或 `npm run build` | 推送不可编译的代码 |
| 5 | **无未解决的合并冲突** | `git status` 无 `both modified` | 合并冲突的代码被推送 |
| 6 | **敏感文件已排除** | 检查 `.gitignore` 配置 | 密钥、本地配置泄露 |
| 7 | **commit message 已审查** | `git log --oneline -n 5` | 不规范或含敏感信息 |

### 3.2 推送操作规范

```bash
# ✅ 正确做法：显式指定仓库和分支
git push origin feat-xxx

# ❌ 禁止做法：无参数推送（可能触发意外的默认行为）
git push

# ❌ 禁止做法：未经确认使用 --force
git push --force origin dev
```

### 3.3 推送后验证

推送完成后，建议立即执行：

```bash
# 验证远程分支与本地一致
git fetch origin
git log origin/dev..dev --oneline    # 查看本地领先远程的提交
git log dev..origin/dev --oneline    # 查看远程领先本地的提交（应为空）
```

## 五、代码评审（Code Review）规范

### 5.1 评审流程

```
开发者创建 PR → 指定评审人 → 评审人反馈意见 → 开发者修改 → 评审通过 → 合并
```

### 5.2 评审检查项

| 类别 | 检查项 |
|------|--------|
| **正确性** | 逻辑是否正确，边界条件是否处理 |
| **安全性** | 无密钥泄露、无 SQL 注入、无 XSS 风险 |
| **性能** | 无 N+1 查询、无不必要的全表扫描 |
| **可读性** | 命名清晰、职责单一、无冗余注释 |
| **一致性** | 代码风格与项目现有代码一致 |
| **测试** | 关键逻辑是否有对应的测试 |
| **文档** | API 变更是否同步更新了文档 |

### 5.3 评审意见分类

| 级别 | 标记 | 含义 |
|------|------|------|
| 🔴 必须修改 | `[blocking]` | 合并前必须解决的问题 |
| 🟡 建议修改 | `[suggestion]` | 推荐改进，但不阻塞合并 |
| 🟢 疑问 | `[question]` | 单纯想了解设计意图 |
| ⚪ 赞赏 | `[praise]` | 写得好的地方 |

## 六、合并策略与操作规范

### 6.1 合并策略选择

| 策略 | 命令 | 适用场景 |
|------|------|---------|
| **Squash Merge**（推荐） | `git merge --squash` + 手动 commit | 功能分支含多个零散 commit，合并为一个语义化 commit |
| **Fast-Forward Merge** | `git merge feat-xxx`（无 `--no-ff`） | 分支线性领先，无分叉历史 |
| **No-Fast-Forward Merge** | `git merge --no-ff feat-xxx` | 需要保留分支痕迹的合并 |

> **团队默认策略**: 优先使用 **Squash Merge**，将功能分支的所有 commit 压缩为一个规范的 Conventional Commit。

### 6.2 Squash 合并标准流程

```bash
# 1. 切换到目标分支并同步最新代码
git checkout dev
git pull origin dev

# 2. 执行 squash merge
git merge --squash feat-xxx

# 3. 提交合并结果（编写规范的 commit message）
git commit -m "feat(scope): 描述

- 变更点1
- 变更点2"

# 4. 确认推送内容（推送前检查清单）
git log --oneline -n 3
git status

# 5. 手动推送（显式指定仓库和分支）
git push origin dev
```

### 6.3 合并冲突处理

```bash
# 1. 更新本地 dev
git checkout dev && git pull origin dev

# 2. 切回功能分支并 rebase
git checkout feat-xxx
git rebase dev

# 3. 解决冲突后继续
git add .
git rebase --continue

# 4. 确认无冲突后推送功能分支
git push origin feat-xxx --force-with-lease
```

### 6.4 合并后操作

| # | 操作 | 命令 |
|---|------|------|
| 1 | 验证构建 | `mvn compile -q` 或 `npm run build` |
| 2 | 删除本地功能分支 | `git branch -d feat-xxx` |
| 3 | 删除远程功能分支 | `git push origin --delete feat-xxx` |
| 4 | 通知团队成员 | 在工作群发送合并通知 |

## 七、常见风险场景与应急预案

### 7.1 误推送（推到错误分支或远程仓库）

**症状**: `git push` 执行后发现推到了不期望的分支/仓库。

**应急方案**:

```bash
# 方案 A：Force Push 回滚（确定无人拉取时使用）
git push --force origin <上一个正确的commit>:<分支名>

# 示例：将 dev 回退到 03b4355
git push --force origin 03b4355:dev
```

> ⚠️ **Force Push 前置条件**: 必须在团队群内确认无人已拉取错误代码，否则会导致其他人的本地历史混乱。

### 7.2 分支状态漂移（文件显示为 deleted）

**症状**: `git status` 显示大量文件为 `deleted`，但磁盘上实际存在。

**原因**: `.git` 目录恢复后，索引记录与磁盘文件不一致。

**应急方案**:

```bash
# 清除 .git/index.lock（如果存在）
Remove-Item -Force ".git/index.lock"

# 用仓库记录覆盖工作区
git checkout HEAD -- .

# 验证修复
git status
```

### 7.3 合并时文件锁定失败（Windows 特有）

**症状**: `git merge` 报错 `Unlink of file 'xxx' failed: Invalid argument`。

**原因**: Windows 进程持有文件句柄，阻止 Git 替换文件。

**应急方案**:

```bash
# 方案 1：重置后使用默认 fast-forward
git reset --hard HEAD
git merge feat-xxx   # 不加 --no-ff

# 方案 2：关闭可能占用文件的 IDE/编辑器后重试
git merge --no-ff feat-xxx
```

### 7.4 Git Index Lock 残留

**症状**: `fatal: Unable to create '.git/index.lock': File exists`。

**原因**: 上一次 Git 进程异常退出，锁文件未清理。

**应急方案**:

```bash
Remove-Item -Force ".git/index.lock"
```

## 八、团队成员职责划分

| 角色 | 职责 |
|------|------|
| **功能开发者** | 在功能分支上开发、编写规范 commit、自测通过后创建 PR |

## 九、违规处理与改进机制

### 9.1 违规记录

以下行为将被记录为团队协作违规：

| 违规行为 | 严重程度 |
|---------|---------|
| 跳过推送前检查清单导致误推送 | 🔴 高 |
| 合并未通过 Code Review 的代码 | 🔴 高 |
| 未经确认使用 `git push --force` | 🔴 高 |
| Commit message 不遵循 Conventional Commits 格式 | 🟡 中 |
| PR 描述未按模板填写 | 🟡 中 |
| 合并后未删除功能分支 | 🟢 低 |

### 9.2 规范迭代

- 本规范随项目实践持续迭代，任何成员可提出修订建议
- 遇到未覆盖的风险场景，在开发记录中记录并补充到第七章
- 每次重大合并事件后进行回顾，检查规范是否需要更新
